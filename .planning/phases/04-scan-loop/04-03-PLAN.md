## Phase Goal

ROADMAP Phase 4 goal (verbatim): The user points the phone at a palm, gets stable live guidance, and captures or imports a photo that is processed and ready to upload, running smoothly on the reference low-end phone.

Note (MVP mode): the Goal line is not in user-story format and no story was invented. Run `/gsd-mvp-phase 4` if a user-story framing is wanted.

Note (wave 2): runs beside 04-02 and 04-04 on disjoint files. It owns CameraPermissionGate's body (04-01 froze its signature) and the fallback screens. Gallery actions call the `onGallery` lambda that ScanScreen passes in; this plan never touches ScanScreen.

Note (UI-SPEC deviation, recorded): UI-SPEC suggests a DataStore "has asked" flag so that "Open settings" never shows before the first system dialog. This plan reaches the same observable rule without a stored flag: the gate always sends a real request on entry while the permission is missing and derives Denied vs PermanentlyDenied only from that request's answer plus the rationale flag. No profile key and no on-disk format are added.

<objective>
Every camera-permission and camera-availability outcome on the Scan route has a clear screen with a way forward: ask again, open settings, try the camera again, or pick a photo from the gallery (SCAN-02; D-04, D-11, D-16).

Purpose: ROADMAP Phase 4 success criterion 1.
Output: pure reducers with JVM tests, the full CameraPermissionGate, stateless fallback screens with a Compose test, en/hi strings.
</objective>
